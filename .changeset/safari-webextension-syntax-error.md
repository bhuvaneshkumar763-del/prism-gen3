Fixed a real bug found live testing the Safari build: `outputSanityCheck.ts`'s `NON_LATIN_SCRIPT`/`NON_LATIN_SCRIPT_GLOBAL` regex — a large Unicode character class used to detect a silently-untranslated non-Latin-script result — failed to parse in Safari's actual WebExtension background-page runtime with `SyntaxError: Invalid regular expression: range out of order in character class`, breaking the entire background script (nothing in the extension could respond to any message). Every codepoint range is correctly ordered and the regex parses fine under Node/V8, Firefox/SpiderMonkey, and even JavaScriptCore's own standalone `jsc` CLI — this is specific to Safari's real WebExtension execution context on this build. A first attempt rewriting the literal's boundaries as explicit `\u{XXXX}` escapes made no difference: the build's minifier normalizes those back into raw characters inside a regex *literal*, so no way of spelling a literal survives it. Fixed by not using a regex literal at all — the character class is now built at runtime via `new RegExp()` from a plain array of `[start, end]` codepoint pairs, which a minifier has no special-case pass for and which may also simply take a different, working parse path in Safari's engine. Confirmed live end-to-end after the fix: a real page translated correctly in Safari with no console errors.

Also documents (`safari/README.md`) the one reliable way found to load this extension for local testing on this Safari version: Develop → Developer Settings… → **Add Temporary Extension…**, pointing at `safari/Prism/Shared (Extension)/Resources` directly. The normal path (installed app → Settings → Extensions) never surfaced the extension in Safari's Extensions list on this system, even though the `.appex` was confirmed correctly registered at the OS level (`pluginkit -m`) — left as an open, unresolved gap rather than a solved one, since Add Temporary Extension is a genuine, if separate, working path.
