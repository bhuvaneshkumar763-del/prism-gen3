Reliability and privacy fix (round-4 audit, item 7): two related same-origin-iframe bugs.

`pageRestore` was registered top-frame-only, like every other popup-facing message handler in `entrypoints/content.ts` — but unlike those (genuinely fine to scope to the top frame, since the popup's own UI only ever needs the main frame's state), a same-origin sub-frame does auto-translate itself. So "Show original" never reached an iframe: the page stayed permanently half-translated, and the sub-frame's mutation watcher kept right on translating new content and sending it to the provider after the user had explicitly asked for the original page back. `tabs.sendMessage(tabId, message)` with no explicit `frameId` already broadcasts to every frame in a tab — the gap was purely that only the top frame ever installed a listener to receive `pageRestore`. Fixed by registering that one handler unconditionally; the other popup-facing handlers stay top-frame-only, unchanged.

`frameLanguageDecisions` (background.ts) is keyed by tabId and was only ever overwritten by the main frame's next report, never cleared on navigation. On an ordinary page navigation, a same-origin sub-frame's content script can run before the new main frame's does — its first `getFrameLanguageDecision` poll could accept the PREVIOUS page's still-present entry immediately, with no way to tell it was stale, including translating a site that IS on `neverTranslateSites` because the inherited entry was left over from a site that wasn't. Fixed two ways: `frameLanguageDecisions` is now proactively cleared the instant a new top-level navigation starts (`tabs.onUpdated`, no new permission needed), and — the actual correctness fix, closing the race the clear alone can't — `FrameLanguageDecision` now carries the reporting frame's own origin, and a sub-frame rejects a decision whose origin doesn't match its own current main frame's origin (read via `window.top.location.origin`) instead of trusting any truthy value blindly.

Both fixes rely on TypeScript + the existing e2e suite for verification — `entrypoints/content.ts` and `entrypoints/background.ts` have no unit test harness today, and building one that can enumerate real Chrome frame ids for a same-origin-iframe scenario is a bigger investment than this fix alone justifies. Live verification (a page with a same-origin iframe, auto-translate on, click "Show original," confirm the iframe reverts too) is recommended before relying on this in a case that matters.
