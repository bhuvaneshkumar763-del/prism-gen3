Fixed the real, primary cause of the permanent "spins forever" translation hang reported live on Orion (iOS), sangtacviet.vip chapter pages — found by comparing the codebase against the last version the user confirmed worked reliably (`v0.3.0-beta.27`) and tracing every change to the messaging/network path since then, after live re-testing ruled out both of the previous release's fixes (the symptom recurred on a fresh app launch's very first translate attempt, before either the concurrency-gate leak or a persistent-background-page teardown could plausibly be involved).

`google.ts`'s `findAuth()` — called at the top of every single `translateBatch()` call to fetch/refresh the auth key its undocumented endpoint needs — had a `fetch()` call with no timeout at all, not even a flawed `AbortController`-based one. Worse, `findAuth()` memoizes its in-flight work into a module-scope `authPromise`, cleared only in a `finally` block that runs after that promise settles. If the fetch never settles (the same real WebKit gap `batchedHttpProvider.ts`'s `sendOnce()` was already fixed for last release — plausibly more likely here specifically, since this scrape hits `translate.googleapis.com`, the exact same host this site's own client-side translate calls hit repeatedly per its own shipped JS), `authPromise` is never cleared, and every future `translateBatch()` call — on any site, for the rest of the background context's life — awaits that same permanently-pending promise. This can trigger on the very first translate of a session, since there's nothing to "leak" first; it just needs the one unguarded fetch to hang once.

Fixed with the same unconditional `setTimeout`-based backstop pattern used for `sendOnce()` last release, covering both the `fetch()` call and the subsequent `response.text()` body read (a stalled body read is the same class of never-settles risk). A timed-out scrape now correctly falls through to the existing hardcoded-fallback-key path — the same path a real scrape failure already took — rather than hanging. Verified via a revert-and-confirm-fails regression test that reproduces the exact unguarded-fetch-never-settles scenario and proves a later, unrelated `translateBatch()` call still completes afterward instead of inheriting a permanently poisoned `authPromise` (confirmed this test genuinely times out without the fix).
