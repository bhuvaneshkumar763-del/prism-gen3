Speed/reliability fix (round-5 bloat audit, release 2): the content script (`matches: ['*://*/*']`, `allFrames: true`) had no guard against a cross-origin sub-frame — the overwhelming majority of real-world ad/tracker/embed iframes. Every such frame paid a full `browser.storage.local.get(null)` config read and a full `PageTranslator` construction (dedupe tracker, `nodesToRestore` map, `mutationWatcher`/`attributeTranslator`/`titleTranslator`/`resweep` instances), even though a cross-origin sub-frame can never receive a `pageTranslate` message (top-frame-only) and never gets an auto-translate decision (gated on the same same-origin check that used to run only after all that construction had already happened). `main()` now checks same-origin first and returns immediately for a cross-origin sub-frame — pure dead weight removed, zero behavior change for the top frame or a same-origin sub-frame.

Also fixed a real latent correctness gap found alongside it: a same-origin sub-frame polled the background for the main frame's auto-translate decision on a fixed 200ms × 15 (~3s) budget, but the main frame's own real worst case — `waitUntilVisible`'s 5s timeout plus language detection's 3s timeout, fully serial — is ~8s. A page opened in a background tab (never visible, burning the full visibility timeout) or with slow detection left every same-origin sub-frame exhausting its poll budget and giving up silently, never translating, before the main frame's own perfectly good decision had even arrived. The two budgets were set independently and drifted apart. `originalLanguageTracker.ts` now exports `VISIBILITY_TIMEOUT_MS` and a derived `MAIN_FRAME_DECISION_WORST_CASE_MS`; `content.ts`'s poll budget is computed from that constant (plus margin for the poll's own round-trip overhead) instead of an independently-chosen number, so the two can't drift apart again.
