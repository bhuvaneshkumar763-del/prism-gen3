Speed fix (round-4 audit, item 5): the concurrency cap was per-call, not per-provider. `runWithConcurrencyLimit` created a fresh `inFlight` counter on every invocation, so the top-level batch dispatch loop and the individual-piece repair retry — despite intending to share one cap — each got their own independent budget, and every separate `translateBatch()` call sharing the one cached provider instance (`background.ts` memoizes it for exactly this reason) got its own budget too. Clicking Translate on a long page could open the main tick's 6 requests, `attributeTranslator.ts`'s own 6, and `titleTranslator.ts`'s 1 — 13 simultaneous requests against a `maxConcurrent` of 6, against a free endpoint that rate-limits by IP.

Fixed by hoisting one shared concurrency gate into `createBatchedHttpProvider`'s closure, alongside the existing `inFlightByKey` dedupe map, so every caller draws from the same budget. This surfaced a real deadlock risk during development: an outer batch task was awaiting its own nested repair-retry dispatch into that same shared gate, which starves the child forever once the adaptive concurrency limit is low enough (verified at `maxConcurrent: 1`, a real value the adaptive-concurrency logic returns on a detected slow connection) that no slot is ever free while the parent still holds one. Fixed by dispatching repair work without the parent awaiting it — the parent's own request is already answered by that point, and each repaired piece's own promise (which the real caller awaits) settles independently of whether the parent's `handleBatch()` call has returned.
