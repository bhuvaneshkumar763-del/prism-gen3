Perceived-speed pass: translation should feel fast, not just be fast. Two real gaps found by reading the actual translate-time path end to end (not delay-gated — both apply on every translate, always):

**Viewport-priority reordering never ran on a typical page.** `viewportPriority.ts`'s `prioritizeByViewport` (translate what's on screen first) was gated behind `queue.length > MAX_PIECES_PER_TICK` (300) — most real pages have well under 300 translatable pieces, so this reordering literally never executed for the common case; the whole page got dispatched in plain DOM order. The gate's own reasoning ("a page that fits in one batch translates everything this tick regardless of order") turned out to be wrong: `batchedHttpProvider.ts` dispatches through its shared concurrency gate in array order (a FIFO semaphore), so a piece queued first still tends to resolve first even within one tick — reordering matters at every page size, not just huge ones. `prioritizeByViewport` itself was also cheaper than the gate assumed (measures each unique block ancestor's `getBoundingClientRect()` once, not per text node). The gate now only checks `queue.length > 1` plus the existing `viewportDirty` cache guard, so every translate — big or small — requests visible content first.

**No motion or progress feedback almost anywhere.** The floating bubble had a spinner; the popup and the selection popup had nothing but a frozen `'Translating…'` label. Added real `(done, total)` progress from `translateLoop.ts` (a new `onProgressChange` listener, mirroring the existing `onWorkingChange` pattern exactly, counted once per node at the same `writeTranslatedNode` choke point every successful write already passes through, coalesced to at most one UI notification per drain so it can't itself introduce jank), wired into the bubble as a slim progress bar under the head title. The popup and selection popup now also get a spinner (reusing the bubble's existing `prismspin` keyframe/`.spinner` pattern) — two of the three translate-triggering surfaces previously showed nothing but static text while busy.

`done` can legitimately settle short of `total` (a genuinely untranslatable fragment gives up after 3 attempts, a node can leave the DOM for good) — this is by design, not a bug: every progress UI hides on the existing `busy` signal going false, the same signal that already hides the spinner, not on `done === total`.
