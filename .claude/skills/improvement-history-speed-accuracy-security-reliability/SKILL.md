# Improvement history: speed, accuracy, security, reliability

This is a ledger, not a changelog restatement — `CHANGELOG.md` has the full
per-release prose. This doc exists so that the next time you're asked to
**"improve"** this extension, you start from what's already been checked and
fixed instead of re-deriving it. Read this whole file before starting a new
audit. When you finish one, add a new dated entry at the top of the relevant
category (or a new "Audit round N" entry below) — don't let this file go
stale, it's only useful if kept current.

**How to use this**: an "improve" request is normally scoped to one or more
of accuracy / speed / security / reliability. Read the matching category
section below first — it tells you what's already fixed (don't re-fix it),
what's been explicitly checked and ruled out (don't re-verify it from
scratch unless you have a specific reason to distrust the earlier check),
and what's open/deferred (a good place to start). Then audit for anything
genuinely new. Every fix logged here was verified against real, live
behavior (the Google endpoint directly, or a real page end-to-end) — not
inferred — and shipped with a regression test proven to fail without the
fix. Match that bar for anything new.

## Accuracy

### Fixed

- **Translation silently did nothing on X.com/Twitter — found via a real user report, reproduced live on their own logged-in account** (beta.39). Reported as "shows translated (green) but does nothing," even on a static single post with nothing new loading — not a scroll/timing issue, a real translation-never-happens bug. Root-caused to two compounding gaps: (1) `outputSanityCheck.ts`'s `NON_LATIN_SCRIPT` regex — the safety net that flags a suspicious identical-output result as a likely silent-echo failure — already *listed* Tamil, Telugu, Kannada, Malayalam, Bengali, Gujarati, Punjabi, Sinhala, Lao, Myanmar, and Georgian in `NON_LATIN_TARGET_LANGUAGES` (the target-language exemption set) but never actually matched any of their Unicode block ranges, so a page in one of those scripts echoed back unchanged was invisible to the detector entirely — it fell through to the length-based fallback, which (2) can't distinguish "genuinely already in the target language" from "wrongly detected as the target language" when the page-level guessed source happens to equal the target (verified live: X.com's own English UI chrome — nav, trending sidebar, footer — dominates `originalLanguageTracker.ts`'s whole-page text sample, so a Tamil-heavy feed routinely gets guessed as `'en'`, and when the target is also `'en'` the coincidence read as a correct no-op). Even for the general case (source and target genuinely differ), `batchedHttpProvider.ts`'s existing repair-retry path for a confirmed-suspicious piece kept resending the SAME wrong source language every time, guaranteeing the identical failure on every attempt. Fixed both: added the missing Unicode ranges (BMP-only, no surrogate pairs needed) to `NON_LATIN_SCRIPT`/`NON_LATIN_SCRIPT_GLOBAL`, and the suspicious-piece repair retry now uses `sourceLanguage: 'auto'` instead of the original declared source (scoped to only the pieces flagged suspicious — a plain "missing/no data" piece, unrelated to a wrong source-language guess, still retries with the original source unchanged). Verified live, repeatedly, against the reporting user's real account: the exact static post that previously showed "translated" with unchanged Tamil text now translates correctly, confirmed on a second, never-before-tested post too. Also added Tamil to `languages.ts`'s target-language quick-pick dropdown, which was missing it entirely.

- **Root-caused and fixed the "words jam at block boundaries" gap left open since beta.34** (post-beta.37, unreleased at time of writing). The original finding (42 lowercase-then-uppercase jams on live Wikipedia en→es) was never root-caused — this pass investigated it properly before touching code, since the earlier probe script no longer existed and its methodology wasn't recorded. First finding: re-running a similar regex-based jam scan live showed 164 raw matches, but the OVERWHELMING majority were false positives — legitimate CamelCase brand names and surnames (`OpenAI`, `ChatGPT`, `AlphaGo`, `McCarthy`, `McCorduck`) that inherently contain a lowercase-to-uppercase letter transition, not two words jammed together; a whitespace-COLLAPSED comparison (stripping all spaces/newlines before matching) produced 60 more false positives from ordinary nav-menu items rendered on separate lines. Filtering those out left a small number of genuine candidates, root-caused by inspecting the actual DOM: a sentence immediately following a wiki-style link (`<a>Go player</a>` then a sibling Text node `". The program only taught..."` — the period ending the PREVIOUS sentence, attached with no space to the START of the sibling node in the source, completely normal Wikipedia markup) lost its leading period on translation. Confirmed directly against the live Google endpoint, repeatedly: a leading bare period/comma (no letter before it) is sometimes dropped from the translated output entirely — inconsistent (a short artificial fragment round-tripped it fine in the same testing) so it can't be relied on and must be handled deterministically on this side, same reasoning as the ALREADY-FIXED trailing-whitespace-stripping quirk (beta.33). Also confirmed live: the symmetric TRAILING case (a node ending in bare punctuation, no trailing whitespace) round-trips correctly — every trailing-punctuation probe came back intact — so only the leading side needed fixing. `translateLoop.ts`'s existing `originalWhitespace` capture/restore mechanism (built for beta.33's whitespace fix) was widened from "leading WHITESPACE" to "leading run of non-letter, non-digit characters" (digits deliberately excluded — a leading digit is often meaningfully part of the sentence, e.g. `"3D printing"`, and no bug was found there) — write-back now also strips any leading non-letter/non-digit run Google's own output happens to have (its behavior is inconsistent, so the captured ORIGINAL must always win) before prepending the correct captured prefix, avoiding double punctuation when Google DID preserve its own copy. Verified live: the exact real Wikipedia sentence that motivated this now reads `"...Jugador de Go. El programa solo enseñaba..."` (period restored) instead of `"...Jugador de GoEl programa..."`.

- **Attribute translation (`placeholder`/`alt`/`value`/`title`) was entirely unbuilt** (post-beta.37, unreleased at time of writing). Search boxes, image alt text, button labels, and tooltips stayed in the original language even on an otherwise fully-translated page, since none of them are `Text` nodes `translateLoop.ts`'s own walk ever reaches. New subsystem, `attributeTranslator.ts` (shaped like `titleTranslator.ts`, per the original deferral note — its own module, not folded into `translateLoop.ts`'s `Text`-node-only machinery), plus a new `collectAttributeTargets` in `collectTextNodes.ts` matching TWP's real target set exactly (confirmed live): `placeholder` on `input`/`textarea`, `alt` on `area`/`img`/an image-type `input`, `value` on a button/submit/reset `input` only (a text/email/etc. input's `value` is real user data, never touched), `title` on any element. One real design gap found while building the discovery walk: `isNoTranslateNode`'s `SKIP_TAGS` set (which includes `TEXTAREA`, since a textarea's typed CONTENT must never be touched) can't be reused wholesale for attribute discovery, or a textarea's own `placeholder` — exactly one of the attributes this feature exists to translate — would be silently excluded too; same issue for an icon-font-classed element's own `title` and a `<code title="...">` tooltip. Fixed by splitting "hard exclude this element's own attributes" (`translate="no"`/`.notranslate`/`isContentEditable` only) from "don't descend into this subtree" (the full `isNoTranslateNode`, unchanged, for children). Dynamic content handled via a `MutationObserver` (childList for new elements, attributes for value changes) with the same own-write loop-guard pattern as `mutationWatcher.ts`'s `noteOwnWrite` — verified via a test that specifically drives the guard through a PAGE-initiated change (not the initial translate, which can't exercise it: the observer only starts watching after that first write already completed, a distinction the first draft of this test missed and had to be corrected before it actually caught anything). Verified live against real Wikipedia: `"Search Wikipedia"` → `"Buscar en Wikipedia"` (placeholder), `"The Free Encyclopedia"` → `"La enciclopedia libre"` (alt text), and `restorePage()` correctly reverted every attribute back to its original value.
- **Google sentence-context grouping, plus a real reflow-corruption bug found while verifying it live** (post-beta.37, unreleased at time of writing). `descriptors.ts`'s `batchingHint` is re-enabled for Google (`{groupByBlock: true, maxGroupChars: 2000}`, matching LLM's value) — previously one-node-per-piece only, so an inline `<b>`/`<a>`/`<span>` split a sentence into fragments translated with zero context (verified live: "left" translated as the direction instead of the verb in "She left the party"). This reopens the exact reflow risk beta.13 reverted grouping for — Google can merge translated content across a piece's own `<a i=N>` node boundaries for some language pairs — so `google.ts` now has its own repair mechanism: `needsRepair` checks a grouped piece's decoded result for (a) fewer entries than nodes were sent (an index got absorbed into a neighbor, the primary reflow signature) and (b) literal, never-actually-parsed `<a i=N>`/`</a>` marker text remaining in a decoded value (a secondary signature, found ONLY via live testing — see below). Either trigger fires an immediate, CONTAINED repair: the group's original per-node strings are re-sent as N individual single-item pieces through the SAME `translateBatch` (reusing the existing single-item padding path), never routed through `batchedHttpProvider.ts`'s generic missing/suspicious retry (which would just resend the same multi-item wire text and could reflow again indefinitely). `onPieceComplete` (incremental write-back) is wrapped so a grouped piece needing repair is held back and forwarded only once its final, repaired value is ready — never the raw reflowed intermediate, avoiding a garbled-text flash on screen. **Real bug found via the mandatory live-page verification** (this exact mechanism's own incident history — beta.13 — is why that verification step was non-negotiable, not skippable in favor of unit tests alone): the FIRST live run against Wikipedia showed literal `<a i=33>` markup, including a duplicated clause, spliced directly into the visible page. Root cause: a large, citation-heavy group's response had its tag structure break partway through (the tokenizer's regex requires a tag's content to contain no further `<`, so a malformed/nested occurrence stops it matching), and everything after that point folded in as untagged "orphan" text — literal markup and all — onto the nearest preceding index. The reconstructed array's LENGTH still matched what was sent in this exact case (a later index padded `.length` back up even though an earlier slot absorbed the leak), so the length-mismatch check alone missed it — the marker-leak check was added specifically because of this live finding, not anticipated in the original design. Reproduced deterministically in a unit test from the exact failure shape, then re-verified live (multiple Wikipedia passes, an order-safe language and a routinely-reflowing one) with no further markup leaks or content corruption found — genuinely repeated content spotted during verification (a benchmark stat, a citation footnote) was confirmed present in the SOURCE Wikipedia HTML itself, not translation-introduced.
- **A same-origin iframe always translated with the literal `'auto'`, never the page's actually-detected language** (beta.37). `content.ts` only calls `originalLanguageTracker.start()` for the main frame — a sub-frame's own tracker instance sits at `'und'` forever, and its `getSourceLanguage` callback falls back to `'auto'`. The relay protocol that already exists specifically so a sub-frame inherits the main frame's decision (`reportFrameLanguageDecision`/`getFrameLanguageDecision`) only ever carried `targetLanguage`, not the detected source language — this is the exact `'auto'` silent-no-op input beta.29 replaced everywhere else, just never covered here. `FrameLanguageDecision` now also carries `originalLanguage`, and the sub-frame passes it through as an explicit `sourceLanguage` to its own `translatePage()` call (normalizing `'und'` → `'auto'` the same way the main frame's own `getSourceLanguage` does, since `sourceLanguageOverride` — unlike the ambient path — has no fallback handling of its own).
- **The tab title ignored a manually-forced source language** (beta.37). The bubble's From picker (`translatePage()`'s second argument) correctly applied to every body text node's translate request but `titleTranslator` was wired to `options.getSourceLanguage` directly, bypassing `sourceLanguageOverride` entirely — a page mis-detected and manually corrected via the picker translated correctly everywhere except the title.
- **Dynamically-added content inside a skip tag was translated anyway** (beta.35). `mutationWatcher.ts` only checked a mutation's own added node (or, for a characterData change, its immediate parent) against the no-translate rules — never any ancestor further up. A syntax highlighter rewriting `<code>`'s innerHTML with plain `<span>`s, or a chart library appending `<text>` labels into an existing `<svg>`, both add nodes that are themselves ordinary tags; only some ancestor is the real skip tag. Now walks the full ancestor chain via a new `hasNoTranslateAncestor` helper.
- **KaTeX-rendered math formulas got mistranslated** (beta.35). Skipping `<math>` only protects KaTeX's hidden MathML copy — the visible rendering (`.katex-html`) is plain `<span>`s (`<span class="mop">sin</span>` for the trig function), so "sin" got translated as the ordinary English word. `.katex` (the outer wrapper around both renderings) is now skipped as one unit.
- **Only 2 of 8 official Material icon-font class variants were recognized** (beta.35). `material-icons-outlined`/`-round`/`-sharp`/`-two-tone` and `material-symbols-rounded`/`-sharp` were missing, so a site using any of them got its icon ligature text translated.
- **An `<option>` with no `value` attribute could have its form-submission value silently changed** (beta.35). Per the HTML spec it submits its own text as the value — translating that text changes what the form actually submits. Now skipped when there's no explicit `value`.
- **A node whose translation kept failing while other content in the same batch kept succeeding could be silently abandoned forever** (beta.35). `noteMissingResult`'s 1.5s retry cooldown used to just `return` when a retry landed inside it — dropping the node out of the queue and every future consideration, since resweep's own backstop can't rescue it either (its `lastSeenText` already matches the still-untranslated content). Now schedules a real retry once the cooldown actually elapses (`cooldownRetryScheduled` guards against piling up duplicate timers).
- **A node the page updated in place while its translation was in flight could be silently overwritten with a stale translation** (beta.35). Write-back only ever checked `node.isConnected`, never that `node.data` was still the text actually SENT — a live-updating node (a score, a chat message) stays connected the whole time. Now verifies the sent text still matches before writing (`sentText` map, kept in sync after every write so the incremental-write-back path's own intentional double-write doesn't mistake its own prior write for an external change), re-queueing for fresh translation otherwise.
- **A node that disconnected while its whole batch failed could be permanently stuck untranslated** (beta.35). Both batch-failure paths (`allFailed`, thrown exception) filtered disconnected nodes out of the retry queue but — unlike the success path — never cleared their `lastSeenText` entry, so a recycled/virtualized-list node reattached later with unchanged content was never picked back up.
- **beta.33's own silent-failure detector had a false positive** (beta.35). `hasScriptMismatch` fired on any text containing even ONE incidental non-Latin character — a physics variable like "Δt", a foreign-script proper noun in an English sentence — wasting a repair request and retry ticks on text that was correct all along. Now requires the overwhelming majority (≥80%) of the text's actual letters to be non-Latin, not just the presence of one.

- **Trailing whitespace stripped by Google, jamming adjacent words together** (beta.33). Confirmed live: Google strips trailing whitespace from a piece's own translated content (`" start with either "` → `"comenzar con cualquiera"`, both ends gone) — independent of the padding-slot reflow issue below. Any page with inline markup (`<p>Read <b>more</b></p>`) could write back jammed ("ReadMORE"). Fixed generically in `translateLoop.ts`: each source Text node's own leading/trailing whitespace is captured before translating and re-applied at write-back, provider-independent. This was the plan's original Finding-1 recommendation — a narrower version (below) shipped first and this general fix was found missing during real-page verification of the batch-size change.
- **Google's padding-slot reflow could silently drop real content** (beta.32). The beta.28 single-item-piece padding fix (below) could have real translated content reflow into the throwaway padding slot, silently discarded by a `.slice(0, 1)` trim. Now reconstructs the full result by joining every slot back together.
- **Selection-translate silently failing on short text** (beta.33). Page translation was fixed in beta.29 (below) to use the page's detected language instead of literal `'auto'`; the selection popup never got the same fix. Now shares the same detected-language fallback.
- **Silent-failure detector missed the short strings it was built for** (beta.33). The identical-output check only flagged results 40+ chars, but Google's silent-echo failure mode overwhelmingly hits short strings (nav labels, buttons). Now also flags any identical result whose script (CJK/Cyrillic/Arabic/etc.) doesn't match what the target language implies, at any length.
- **MathJax formulas, SVG icon text, icon-font ligatures mistranslated** (beta.33). Matched against TWP's real skip list: `<svg>`, `<template>`, `<math>`, `<mjx-container>`, `<tex-math>`, plus `material-icons`/`material-symbols-outlined` classes are now skipped — none were before.
- **`'auto'` source language silently failing** (beta.29). Google's auto-detection silently echoes text back unchanged (real `200`, no error) for a lot of real content. Page translation now sends the page's own detected language (via `tabs.detectLanguage`, with a text-sample fallback) instead of the literal string `'auto'`.
- **Single-string pieces unreliable on Google's endpoint** (beta.28). Google's endpoint only reliably translates a piece wrapped in `<a i=N>` markers, which only kicked in for multi-string pieces. Now every single-string piece is padded with a throwaway second string before sending.
- **Manually-pinned source language forced onto every future request** (beta.22). Selecting a language used to persist and override the provider's own per-request auto-detection forever. Now force-retranslates once, then a fresh page load goes back to auto-detection.
- **`<html lang>` falsely excluding whole pages** (beta.23). A per-node lang check almost always resolved to `<html lang>`, which reflects UI language, not content language (pixiv.net: `lang="en"` UI, Chinese novel content) — excluded 100% of matching pages. Check removed entirely, matching TWP (no equivalent check).
- **Tag/link clusters scrambled by cross-piece batching** (beta.5, beta.9, beta.27). Hashtags, `#go#be`-style chains, and nav/breadcrumb link clusters (`« Prev | Chapter 12 | Next »`) were batched into shared multi-item pieces and came back reordered/merged/scrambled. Each is now isolated into its own piece.
- **Shadow-DOM content structurally invisible to translation** (beta.13, and again more thoroughly at v0.2.1/Session 10). `element.childNodes` never includes shadow-root content — the DOM walk now crosses open shadow-root boundaries recursively.
- **Google reflow across grouped-node boundaries** (beta.13). Grouping multiple DOM text nodes into one request for extra context let Google reflow translated text across those internal boundaries (duplicated/merged fragments, stray leading punctuation). Reverted to one-node-per-piece for Google, matching every other provider.
- **`<pre>`/`<code>` defaults wrong** (beta.24, beta.25). `<pre>` was hardcoded skipped (broke prose-in-`<pre>` forum pages), then the "translate `<pre>`" toggle shipped defaulted off (broke it the other way) — TWP's real default is translate-on. Matched exactly, with the bare-whole-page `<pre>` exception TWP also has. `<code>` stays protected always.
- **No-letters text mistranslated** (v0.3.0-beta.16-adjacent). Chapter-count filter chips like `"> 100"` came back reworded as `"compare 100"`. Text with no letters at all is now skipped from collection.

### Checked and ruled out (don't re-verify from scratch)

- **HTML entity round-tripping** — `escapeHTML`/`unescapeHTML` handle `&amp; &lt; &gt; &quot; &#39;` correctly, decode-last ordering for `&amp;` verified live.
- **Language code coverage** — `zh/zh-CN/zh-TW/he/iw/no/nb/id/in/pt/pt-BR` all verified against the live endpoint; `zh-TW` correctly returns Traditional.
- **URLs, version strings, code snippets** pass through unmangled. One minor known gap, not scoped: `a.b@c.io` → `ab@c.io` (a dot dropped from an email local-part), low frequency.
- **Positional array alignment at scale** — verified directly at 40/120/300 pieces sharing one request: 0 misaligned. The batching-budget-based misalignment theory doesn't hold; the real reflow risk is within a single piece's `<a i=N>` markers, already handled separately.

## Speed

### Fixed

- **`zod` was 51% of the shipped extension's bytes — round-5 bloat audit** (beta.52). You asked for a straight bloat audit ("any overloading or waste") rather than a bug hunt. Measured by stubbing the `zod` import in `src/shared/config/schema.ts` and rebuilding: total build size 393.17KB → 191.12KB, a 202KB (51%) delta. It landed THREE separate times (`content-scripts/content.js` 142.58→75.17KB, `background.js` 95.09→27.77KB, the options page's own `siteOverrides-*.js` chunk 88.56→21.25KB) because content scripts can't share a chunk with the background graph. Combined with the content script's `allFrames: true` and — a separate finding, see below — no frame-triage guard, ~67KB of validation-library code was parsed in every iframe of every page visited, all to validate 23 flat config keys (7 strings, 7 booleans, 5 string arrays, 2 enums, 2 records, 1 small nullable object) at exactly three call sites, none of which used any of zod's transforms, coercion, defaults, or refinements. Replaced with a hand-written `src/shared/config/validate.ts` — a per-key validator table, not a schema-builder abstraction (deliberately no generic combinator library; 23 keys of flat data doesn't warrant one). `Config` (`schema.ts`) is now a hand-written interface instead of `z.infer<typeof configSchema>` — the one real cost of the removal, since the type no longer derives from the same source as its validation — mitigated by typing `configValidators` as a mapped type over `Config` (`{ [K in ConfigKey]: Validator<Config[K]> }`), which makes an added-but-unvalidated field a compile error, restoring the same static coupling `z.infer` gave for free. Two zod behaviors preserved deliberately: unknown keys silently dropped rather than rejected (a settings file from a newer build must still import on an older one), and `bubblePosition`'s inner object stripping its own unknown keys too. Actual measured result after shipping: 393.17KB → 194.04KB (the extra ~3KB vs. the stub measurement is the validator module's own code, expected). Every pre-existing config test (`configStore.test.ts`, `migrations.test.ts`, `backup.test.ts`) passed UNCHANGED — the real regression signal for a change like this, since editing any of them would have meant the replacement's semantics diverged from zod's. `guard:bundle-size`'s `MAX_BYTES` (1MB against a 286KB baseline) is exactly why this went unnoticed for 51 releases — see the Audit round log entry below for the follow-up to actually fix that headroom.
- **Idle-page cost paid per frame, unconditionally — round-5 bloat audit, release 2** (beta.53). The content script (`matches: ['*://*/*']`, `allFrames: true`) had no guard against a CROSS-ORIGIN sub-frame — the overwhelming majority of real-world ad/tracker/embed iframes. Every such frame paid a full `configStore.onReady()` → `browser.storage.local.get(null)` round trip AND a full `createPageTranslator()` construction (dedupe tracker, `nodesToRestore` map, `mutationWatcher`/`attributeTranslator`/`titleTranslator`/`resweep` instances), even though a cross-origin sub-frame can NEVER receive a `pageTranslate` message (that handler is registered top-frame-only) and NEVER gets an auto-translate decision (gated on the exact same same-origin check that used to run only AFTER all that construction had already happened, deep inside the sub-frame branch). `main()` (`entrypoints/content.ts`) now performs that same-origin check FIRST and returns immediately for a cross-origin sub-frame — this only short-circuits a case that was already provably, permanently inert; zero behavior change for the top frame or a genuinely same-origin sub-frame, confirmed by the full e2e suite passing unchanged (content-script injection, bubble-present checks). A second, sharper bug was found alongside it: a same-origin sub-frame's decision-poll budget (`content.ts`, `POLL_INTERVAL_MS * MAX_ATTEMPTS`, previously a fixed `200ms x 15 ≈ 3s`) was SMALLER than the main frame's own real worst case — `waitUntilVisible`'s 5s timeout plus language detection's 3s timeout, fully serial, ≈8s (`originalLanguageTracker.ts`'s `start()`). A page opened in a background tab (never visible, so `waitUntilVisible` burns its full timeout) or with slow detection left EVERY same-origin sub-frame exhausting its poll budget and giving up silently — never translating — before the main frame's own perfectly good decision had even arrived: real waste (up to 15 wasted background round trips per sub-frame) and a real correctness gap from the same root cause, two independently-set timing budgets on either side of one relay that were never reconciled. Fixed by naming and exporting the previously-inline `5000` visibility timeout as `VISIBILITY_TIMEOUT_MS` and deriving a new `MAIN_FRAME_DECISION_WORST_CASE_MS = VISIBILITY_TIMEOUT_MS + DETECT_LANGUAGE_TIMEOUT_MS` from it (`originalLanguageTracker.ts`); `content.ts`'s `MAX_ATTEMPTS` is now computed from that constant (plus a small margin for the poll's own round-trip overhead) instead of an independently-chosen number, so the two cannot drift apart again. **Test-coverage note, same precedent as items 7/8 below**: `content.ts`'s own frame-triage guard and poll-budget usage have no dedicated automated test — this repo has no unit harness for `entrypoints/content.ts`, and the e2e harness can't target a specific sub-frame's response without adding a `webNavigation` permission (deliberately not added, same reasoning as items 7/8). What IS directly unit-tested: `MAIN_FRAME_DECISION_WORST_CASE_MS`'s derivation itself (`originalLanguageTracker.test.ts`), locking down the actual number so the two budgets can't silently drift apart again even without a `content.ts`-level test — reverted-and-confirmed-failing. The existing e2e suite (unchanged, still fully passing) is the regression signal that the guard doesn't break the top-frame case, which is the one it CAN exercise.
- **`guard:bundle-size` retightened, plus the round's remaining small stale items — round-5 bloat audit, release 3, final release of this round** (beta.54). `scripts/check-bundle-size.mjs`'s `MAX_BYTES` was 1MB against a ~286KB Session-8 baseline (~3.5x headroom) — the exact reason `zod` tripling itself across bundles (202KB, beta.52's fix) went unnoticed for 51 releases; a guard with that much slack only catches a MASSIVE regression. Retightened to 300KB, ~1.5x the real ~194KB total measured after beta.52/beta.53. Also: `remoteTranslator.ts`'s `TRANSLATE_PIECES_TIMEOUT_MS` doc comment corrected a stale "~62s worst case" claim — `batchedHttpProvider.ts`'s `OVERALL_DEADLINE_MS = 30000` (round-4 item 5) now bounds a SINGLE `translateBatch()` call's retry sequence at 30s, not ~62s; the 90s timeout value is still correct because one `translatePieces` request can span multiple batches serialized through the shared concurrency gate, but the comment's stated reasoning needed fixing — value unchanged, pending a future live-measured re-tune. `collectTextNodes.ts`'s `isWholePageBarePre` was `export`ed but used only inside its own file (confirmed via repo-wide grep including tests) — un-exported. This closes round 5's planned work; the DOM-mutation double-traversal (Speed > Open/deferred above) remains the one open item, explicitly deferred by request.
- **Perceived-speed audit: viewport-priority reordering never ran on a typical page, and two of three translate-triggering surfaces showed nothing but a frozen label while busy** (beta.55). You asked to make translation feel fast in BOTH the delayed and the normal case, not detect-then-react to slowness — read the actual translate-time path end to end rather than turning your two example ideas into the whole plan. Two real, always-on fixes (no "is this slow?" branch anywhere): (1) `viewportPriority.ts`'s `prioritizeByViewport` (translate on-screen content first) was gated behind `queue.length > MAX_PIECES_PER_TICK` (300) in `translateLoop.ts` — most real pages have well under 300 translatable pieces, so this reordering literally never executed for the common case, dispatched in plain DOM order instead. The gate's own comment reasoned "a page that fits in one batch already translates everything this tick regardless of order" — checked directly and that's wrong: `batchedHttpProvider.ts` dispatches groups through its shared concurrency gate in array order (a FIFO semaphore, `batches.map((batch) => concurrencyGate.run(...))`), so a piece queued first still tends to RESOLVE first even within one tick. Also checked the actual cost `prioritizeByViewport` was being gated against: it measures each unique BLOCK ancestor's `getBoundingClientRect()` once (memoized per block, not per text node), cheap for a typical page's handful-to-low-hundreds of blocks — the gate solved a real problem (don't re-measure a huge page needlessly) but silently disabled the whole feature for the common case as a side effect. Fixed: gate is now just `queue.length > 1` (plus the pre-existing, legitimate `viewportDirty` cache guard) — reordering runs on every translate, not just huge ones. ## Reliability

### Fixed

- **Rapidly skipping chapters wedged the tick loop — spinner spinning forever, recovering only on a reload or on skipping to the page AFTER it** (beta.62). Reported live once the earlier saga (above) was confirmed resolved in beta.61: rapid page-skipping worked two or three times, then the next chapter spun forever. That recovery signature — any *subsequent* cycle clears it — pointed straight at overlapping translate cycles, which rapid navigation produces by design: a new `translatePage()` starts while the previous chapter's batch is still in flight. Two real defects found in `translateLoop.ts`, both specific to that overlap: (1) **a stale cycle cleared the in-flight flag for a newer, live one** — `batchInFlight = false` lives in the tick's `finally`, and a `return` inside `try` still runs `finally`, so an OLD cycle's batch resolving and correctly bailing out on the `requestedUnderGeneration !== cycleGeneration` check still wiped the flag a NEWER, still-running tick had just set, making `isWorking()` report idle while a batch was genuinely outstanding; fixed by keying the flag on generation (`inFlightGeneration`) so only the cycle that set it can clear it, the same `if (x === mine)` discipline `translationRoutine`'s `finally` already used for `runningForGeneration`. (2) **a dropped wake could leave the loop with no scheduled successor** — the re-entrancy guard (`if (runningForGeneration === cycleGeneration) return;`) discards a wake outright, which was only safe on the assumption that the already-running tick reschedules at its tail, but the generation-mismatch bail-outs `return` *before* reaching that tail; together those could strand a non-empty `queue` with no tick pending and nothing to restart it (`working` stuck true until an external event kicked it). Fixed structurally rather than per-path: `runTranslationTick` now reports whether it scheduled its own successor, and `translationRoutine`'s `finally` schedules one whenever it didn't and real work remains — so "a tick always schedules its successor" is an invariant of the loop instead of something every future early-return has to remember. Defect (1) shipped with a revert-and-confirm-fails regression test (confirmed failing before, passing after); a second convergence test drives several rapid chapter switches with out-of-order batch resolution and asserts the settle-state invariant (queue drained, spinner off). **CONFIRMED FIXED on-device** by the reporting user against beta.62 (same repro: translate a chapter, then rapidly skip several pages). Scope note kept for the record: the convergence test passes on the pre-fix code too, so only defect (1) had a test that reverted-and-confirmed-failing; defect (2) was a proven-real structural hole closed on its own merits rather than a mechanism empirically tied to the report. Since the two shipped together and the live symptom is gone, which of them was load-bearing is not established — if anything in this area regresses later, treat both as in-scope.

- **The real, primary cause of the "spins forever" Orion/iOS hang: `google.ts`'s `findAuth()` had an entirely unbounded `fetch()` call whose in-flight promise, once hung, permanently poisoned every future translate for the rest of the session — found by comparing the codebase directly against the last known-good tag (`v0.3.0-beta.27`)** (beta.60). Verified via a revert-and-confirm-fails regression test reproducing the exact unguarded-fetch-never-settles scenario, confirming a later, unrelated `translateBatch()` call still completes afterward (confirmed this test genuinely times out without the fix, per this project's standing discipline). Same caveat as beta.58/beta.59: not confirmed via live device inspection (unavailable from this environment) — grounded in direct code reading and a mechanism that fully explains every reported symptom, not a guess, but the user's own device is still the final check.

- **beta.58's `background.persistent: false` for every MV2 build was itself a regression on Orion — found via live user re-testing that showed the exact same "stuck spinning" symptom recurring immediately after updating** (beta.59). beta.58's own reasoning (below) was real for the Safari-wrapped app but over-generalized: Orion, loading the extension directly rather than through Apple's native Safari-Extension framework, implements its own background-page lifecycle, not Chrome's real MV3 service-worker model. beta.44 (see `CHANGELOG.md`) had already root-caused and fixed a "stuck busy spinner forever on mobile" bug on this exact same site, tracing it to the background context dying MID-REQUEST under mobile memory pressure and permanently orphaning an in-flight message — `remoteTranslator.ts`'s 90s `withTimeout` bounds any ONE such orphaned request, but a text-dense chapter page needs several sequential round trips, so repeated mid-request deaths still add up to several real, user-visible minutes of spinning. - **Sub-frames never got a `pageRestore`, and could inherit the PREVIOUS page's auto-translate decision on navigation — round-4 audit, item 7** (beta.48). - **A rejected/expired Google auth key was never invalidated, and a persistently-broken provider could look identical to "correctly declining to translate," moved here from this category's own Open/deferred entry** (beta.45). - **A `translatePieces` messaging round trip with no timeout could pin the busy spinner permanently on mobile, recoverable only by reloading the page — real user report** (beta.44). - **A partial provider outage could report success while silently leaving whole regions of a page untranslated, no error ever shown — round-4 audit** (beta.42). Failure detection was all-or-nothing: `allFailed` requires EVERY outcome in a tick to fail, but a rate-limited/degraded provider's normal shape is a MIXED batch (`batchedHttpProvider.ts` splits a tick into many HTTP sub-requests, and each sub-request's failure is confined to its own pieces) — so a genuine, ongoing partial outage (most pieces failing, a few still landing) took the success-path branch on every single tick, which unconditionally reset `consecutiveBatchFailures`/`surfacedErrorStreak` to zero and cleared any surfaced error. The failing pieces still went through `noteMissingResult`'s existing bounded (give-up-after-3) per-node retry and were eventually abandoned in the background — but with the failure counters wiped every tick, that abandonment produced no visible signal at all: `working` clears, the bubble shows the normal green "translated" state, and the untranslated regions just stay that way. Fixed by only resetting the counters on a tick with NO genuine (non-`'suspicious'`) failures — a batch that's fully successful, or one whose failures are all confirmed-suspicious (the beta.36 endonym case), still resets exactly as before; a batch with any real network/HTTP/parse failure now correctly accumulates toward `CONSECUTIVE_FAILURES_BEFORE_SURFACING`, the same way a fully-failed batch already did. Writing a regression test for this needed the same care as the restore-race fix above: an `err(...)` outcome for a node ALONE in its batch takes the unrelated `allFailed` path instead of exercising the mixed-outcome branch under test, and — subtler — even with TWO nodes in the same batch, if the always-failing one is left to cycle through `noteMissingResult`'s own 1500ms per-node cooldown, most ticks in a companion-refresh loop end up with that node simply absent (mid-cooldown), trivially resetting the counter and masking the bug; refreshing BOTH nodes on every cycle (bypassing that unrelated per-node cooldown for both) is what actually keeps a genuine failure present in every tick, matching the real shape of a degraded provider failing a fraction of a large page's many different pieces continuously, not one single node stuck cycling through its own retry backoff.
- **Clicking "Show original" while a retry was pending could permanently spin the tick loop and lock the primary button disabled — round-4 audit** (beta.41). `noteMissingResult`'s cooldown-retry timer (a plain `setTimeout`, scheduled when a piece's retry landed within 1500ms of its last attempt) carried no check tying it to the translate cycle it was scheduled under. `restorePage()` empties `queue`, bumps `cycleGeneration`, and moves `pageLanguageState` back to `'original'` — but cannot cancel an already-scheduled timer. With identical code, that difference cannot be a code regression: it was environmental, overwhelmingly likely the unofficial Google endpoint rate-limiting the user's IP, accumulating across a testing session run in ascending version order (each later version tested with more quota already burned) — and aggravated on that specific site because the page's own JS independently hammers `translate.googleapis.com` from the same IP. **Lesson for future sessions: when a user bisects a regression, diff the tags before theorizing — and treat "each successive version is worse" as a possible test-order/rate-limit confound rather than a code gradient.** Do not re-chase this; do not re-propose any of the four investigated mechanisms as "the fix" without genuinely new evidence.

## Security

### Fixed

- **A manual translate in an incognito window wrote the page's source text into the NORMAL profile's on-disk translation cache — round-4 audit, item 8** (beta.49). Extensions run in "spanning" mode by default (one shared background service worker across normal AND incognito windows), so `translatePiecesWithCache` (background.ts) ran identically regardless of which kind of window a request came from — `translationCacheEnabled` said nothing about that, and `isIncognito` was only ever consulted in the unrelated auto-translate-decision path (`autoTranslateDecision.ts`). The cache key itself contains the source text (`cacheKeyFor(providerId, sourceLanguage, targetLanguage, JSON.stringify(piece))`), so an incognito translate persisted that content into the normal profile's IndexedDB past the incognito session ending, with no indication to the user it had happened. Fixed by also checking `sender.tab.incognito` (the standard WebExtensions field for exactly this, populated on the real `MessageSender` Chrome hands the handler) before either the cache READ or the cache WRITE — one boolean AND on the existing `cacheEnabled` computation, since both paths already gate on that single flag. While auditing this, the SAME finding's second half — "although `translationCache.clear()` exists, no UI calls it" — turned out to already be fixed: Settings' Advanced tab already has a working "Clear translation cache" button (`entrypoints/options/App.tsx`) wired directly to `translationCache.clear()`. Corrected here so a future audit doesn't re-flag it. **No dedicated automated test**: `entrypoints/background.ts` has no unit test harness (same gap noted in item 7's own entry above), and this codebase's e2e suite launches a normal, non-incognito persistent Chrome context, so it can't easily construct a real incognito `sender.tab.incognito: true` message without a meaningfully bigger investment in incognito-mode e2e infrastructure than this one-line fix justifies. Verified via `tsc` + the full existing test/e2e suite (all green, confirming no regression); the fix itself is a single, directly-reviewable boolean condition.
- **Any web page could drive the floating bubble and the selection popup as if the user had clicked them — round-4 audit** (beta.40). Neither surface checked `event.isTrusted`, and both mount into an `open` shadow root at a fixed, guessable id (`prism-bubble-host`, `prism-selection-popup-host`), so a page could dispatch synthetic pointer/mouse/keyboard/change events at their internal elements. Real impact, not theoretical: a synthetic click on the bubble's "Always" chip persists the attacker's own hostname into `alwaysTranslateSites`, so every future visit silently auto-translates (shipping the whole page, including anything rendered for a logged-in user, to the configured provider) with no prompt; driving the selection popup's trigger fires unlimited real translate requests with attacker-controlled text through the user's provider, burning a paid key or rate-limiting the free endpoint. Confirmed live, by accident, while debugging an unrelated session issue — driving the bubble via synthetic `PointerEvent`s from page-context JS worked exactly like a real click. Every page-reachable handler in `FloatingBubble.tsx` (button clicks, chip clicks, select changes, the ball's pointer/keyboard toggle) and `mountSelectionPopup.ts` (`onMouseUp`/`onKeyUp`, the trigger click) now rejects an event with `isTrusted !== true` — the standard defense for this bug class, with zero effect on real user interaction (a genuine click/keypress always reports `isTrusted: true`; only a script-dispatched event doesn't). Testing this required a new `tests/trustedEvent.ts` helper (`Object.defineProperty(event, 'isTrusted', {value: true})` before dispatch), since every existing test that simulated a click via `.click()`/`dispatchEvent()` produces `isTrusted: false` in both happy-dom and real browsers — exactly like a page's own synthetic event would, which is what makes the fix testable at all. Deliberately did NOT also switch the shadow roots to `mode: 'closed'`: the `isTrusted` check alone fully closes the demonstrated exploit (it blocks the action regardless of whether the page can reach the element), and `createShadowHost`'s own original design comment already correctly judged the remaining benefit (blocking pure DOM/data inspection) as marginal for these surfaces — doing it anyway would have meant reworking how all 4 affected test files reach into the shadow root for no corresponding security gain.
- **No message-sender validation** (beta.32). `@webext-core/messaging`'s `onMessage` does no sender validation of its own (checked its actual implementation directly). Any other installed extension could send this extension's own message shapes straight to its background/content script and have them processed as if from this extension's own UI — triggering translate/restore, or relaying arbitrary text through `translatePieces` to spend the user's configured provider quota (including a paid key). Every handler in `entrypoints/background.ts` and `entrypoints/content.ts` now rejects unless `sender.id` matches `browser.runtime.id`.

A later round explicitly deprioritized further security work ("security is fine for now") in favor of speed/accuracy — that's a scoping choice for that round, not a finding that nothing else exists. ### Methodology notes carried forward

- **A regex-based "letters jammed together" scan needs false-positive filtering before its match count means anything.** Root-causing the block-boundary jam finding: a live rescan found 164 raw lowercase-then-uppercase matches, but the overwhelming majority were legitimate CamelCase brand names/surnames (`OpenAI`, `ChatGPT`, `McCarthy`) that inherently contain that letter-case transition, not a translation bug — and a whitespace-COLLAPSED comparison (stripping spaces/newlines before matching, done to catch jams across what LOOKS like separate elements) added dozens more false positives from ordinary nav-menu items correctly rendered on separate lines. Only after filtering both categories out did the real signal — 2-3 genuine cross-node jams — become visible. Don't trust a raw match count from this kind of heuristic; inspect actual matches and cross-check against the real DOM before concluding anything.
- **Cast a wide net before narrowing.** Run parallel probes/greps covering multiple hypotheses at once, then go deep on what's real — not one hypothesis investigated to conclusion before starting the next. (Direct user correction, round 2: "it looks like you look one at a time and then get stuck at one.")
- **Verify empirically, not by inference.** Live-endpoint `fetch` probes for provider behavior claims, `gh api` against TWP's real source for "what does the reference implementation do" claims — not assumption or memory.
- **Revert-and-confirm-fails on every fix.** Temporarily break the new logic, confirm the new test fails with the expected message, restore, confirm it passes again.
- **Full real-page verification for anything with prior incident history**, not just unit tests — the batch-size constant specifically (beta.22 history) got a real Playwright run against live Wikipedia through the actual built extension, not just synthetic benchmarks. This is what surfaced the whitespace bug that the unit-test-only rounds had missed.
- **Be precise about progress counts.** Don't bundle a bonus fix found along the way into the count of a numbered finding list — report them separately (direct user correction, round 2).
- **Verify AMO signing via actual log text**, not the green checkmark, every release — see Reliability's AMO entry above.
- **A live-page regression check that looks bad isn't necessarily a regression — confirm against a clean baseline before assuming.** Round 3 part 1's live verification found 42 word-jamming matches on Wikipedia after shipping; before treating it as a new bug, `git stash`'d the changes, rebuilt against the unmodified prior release, and reran the identical probe — same 42 matches, proving it pre-existing (now tracked in Accuracy's Open/deferred). Cheap and fast (a stash + rebuild), and the only way to distinguish "I introduced this" from "this was already here."
- **`batchedHttpProvider.ts`'s own test file has a misleading comment**: `maxBatchChars: 1, // force every piece into its own request` (in the "caps concurrent in-flight" test) does NOT do what it claims — a 1-char piece only reaches `currentChars = 1`, which fails the `> 1` flush check, so it merges with the next piece instead of splitting. That test still passes with the expected request count, but only because of an unrelated repair-retry side effect (the mocked response returns fewer results than pieces sent, triggering individual repair requests), not because of the batching split the comment describes. Found and worked around (used `maxBatchChars: 0`, which genuinely does force a per-piece split) while writing round 3's own concurrency test — not fixed, since it's a pre-existing test only, not product code, and touching it was out of this round's scope. Worth a real look next time that test file is touched.
- **A new "reject stale state" check can trip on the fix's OWN intentional side effects — check for that interaction explicitly, don't just test the new check in isolation.** Round 3 part 2's stale-overwrite fix (`sentText` map, compares `node.data` against what was actually sent before writing) initially produced `"TR:TR:score: 2"` — double-translated — in its own first test run. Cause: the incremental-write-back feature from part 1 deliberately calls the write-back function TWICE per node in the same tick (once via `onPieceComplete`, once again from the always-running final loop, by design — see `writeTranslatedNode`'s doc comment) and relies on that being a harmless no-op. The new staleness check broke that invariant: after the FIRST write, `node.data` no longer matched the ORIGINAL `sentText` entry (it now held the TRANSLATED text), so the redundant SECOND call saw a "mismatch" and mistook its own prior write for an external page update, re-queueing the node to re-translate its own output. Fixed by updating `sentText` to the new value immediately after a successful write, so the redundant pass sees no mismatch. The lesson: when adding a check that compares "what we expect" against live state, audit every OTHER place in the same function/file that also touches that live state — not just the new check's own direct test cases — since two independently-correct pieces of logic can still interact wrongly.
