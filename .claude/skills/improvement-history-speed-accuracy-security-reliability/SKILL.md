# Improvement history: speed, accuracy, security, reliability

This is a ledger, not a changelog restatement — `CHANGELOG.md` has the full
per-release prose. This doc exists so that the next time you're asked to
**"improve"** this extension, you start from what's already been checked and
fixed instead of re-deriving it. Read this whole file before starting a new
audit. When you finish one, add a new dated entry at the top of the relevant
category (or a new "Audit round N" entry below) — don't let this file go
stale, it's only useful if kept current.

**How to use this**: an "improve" request is normally scoped to one or more
of accuracy / speed / security / reliability. Read the matching category
section below first — it tells you what's already fixed (don't re-fix it),
what's been explicitly checked and ruled out (don't re-verify it from
scratch unless you have a specific reason to distrust the earlier check),
and what's open/deferred (a good place to start). Then audit for anything
genuinely new. Every fix logged here was verified against real, live
behavior (the Google endpoint directly, or a real page end-to-end) — not
inferred — and shipped with a regression test proven to fail without the
fix. Match that bar for anything new.

## Accuracy

### Fixed

- **A same-origin iframe always translated with the literal `'auto'`, never the page's actually-detected language** (beta.37). `content.ts` only calls `originalLanguageTracker.start()` for the main frame — a sub-frame's own tracker instance sits at `'und'` forever, and its `getSourceLanguage` callback falls back to `'auto'`. The relay protocol that already exists specifically so a sub-frame inherits the main frame's decision (`reportFrameLanguageDecision`/`getFrameLanguageDecision`) only ever carried `targetLanguage`, not the detected source language — this is the exact `'auto'` silent-no-op input beta.29 replaced everywhere else, just never covered here. `FrameLanguageDecision` now also carries `originalLanguage`, and the sub-frame passes it through as an explicit `sourceLanguage` to its own `translatePage()` call (normalizing `'und'` → `'auto'` the same way the main frame's own `getSourceLanguage` does, since `sourceLanguageOverride` — unlike the ambient path — has no fallback handling of its own).
- **The tab title ignored a manually-forced source language** (beta.37). The bubble's From picker (`translatePage()`'s second argument) correctly applied to every body text node's translate request but `titleTranslator` was wired to `options.getSourceLanguage` directly, bypassing `sourceLanguageOverride` entirely — a page mis-detected and manually corrected via the picker translated correctly everywhere except the title.
- **Dynamically-added content inside a skip tag was translated anyway** (beta.35). `mutationWatcher.ts` only checked a mutation's own added node (or, for a characterData change, its immediate parent) against the no-translate rules — never any ancestor further up. A syntax highlighter rewriting `<code>`'s innerHTML with plain `<span>`s, or a chart library appending `<text>` labels into an existing `<svg>`, both add nodes that are themselves ordinary tags; only some ancestor is the real skip tag. Now walks the full ancestor chain via a new `hasNoTranslateAncestor` helper.
- **KaTeX-rendered math formulas got mistranslated** (beta.35). Skipping `<math>` only protects KaTeX's hidden MathML copy — the visible rendering (`.katex-html`) is plain `<span>`s (`<span class="mop">sin</span>` for the trig function), so "sin" got translated as the ordinary English word. `.katex` (the outer wrapper around both renderings) is now skipped as one unit.
- **Only 2 of 8 official Material icon-font class variants were recognized** (beta.35). `material-icons-outlined`/`-round`/`-sharp`/`-two-tone` and `material-symbols-rounded`/`-sharp` were missing, so a site using any of them got its icon ligature text translated.
- **An `<option>` with no `value` attribute could have its form-submission value silently changed** (beta.35). Per the HTML spec it submits its own text as the value — translating that text changes what the form actually submits. Now skipped when there's no explicit `value`.
- **A node whose translation kept failing while other content in the same batch kept succeeding could be silently abandoned forever** (beta.35). `noteMissingResult`'s 1.5s retry cooldown used to just `return` when a retry landed inside it — dropping the node out of the queue and every future consideration, since resweep's own backstop can't rescue it either (its `lastSeenText` already matches the still-untranslated content). Now schedules a real retry once the cooldown actually elapses (`cooldownRetryScheduled` guards against piling up duplicate timers).
- **A node the page updated in place while its translation was in flight could be silently overwritten with a stale translation** (beta.35). Write-back only ever checked `node.isConnected`, never that `node.data` was still the text actually SENT — a live-updating node (a score, a chat message) stays connected the whole time. Now verifies the sent text still matches before writing (`sentText` map, kept in sync after every write so the incremental-write-back path's own intentional double-write doesn't mistake its own prior write for an external change), re-queueing for fresh translation otherwise.
- **A node that disconnected while its whole batch failed could be permanently stuck untranslated** (beta.35). Both batch-failure paths (`allFailed`, thrown exception) filtered disconnected nodes out of the retry queue but — unlike the success path — never cleared their `lastSeenText` entry, so a recycled/virtualized-list node reattached later with unchanged content was never picked back up.
- **beta.33's own silent-failure detector had a false positive** (beta.35). `hasScriptMismatch` fired on any text containing even ONE incidental non-Latin character — a physics variable like "Δt", a foreign-script proper noun in an English sentence — wasting a repair request and retry ticks on text that was correct all along. Now requires the overwhelming majority (≥80%) of the text's actual letters to be non-Latin, not just the presence of one.

- **Trailing whitespace stripped by Google, jamming adjacent words together** (beta.33). Confirmed live: Google strips trailing whitespace from a piece's own translated content (`" start with either "` → `"comenzar con cualquiera"`, both ends gone) — independent of the padding-slot reflow issue below. Any page with inline markup (`<p>Read <b>more</b></p>`) could write back jammed ("ReadMORE"). Fixed generically in `translateLoop.ts`: each source Text node's own leading/trailing whitespace is captured before translating and re-applied at write-back, provider-independent. This was the plan's original Finding-1 recommendation — a narrower version (below) shipped first and this general fix was found missing during real-page verification of the batch-size change.
- **Google's padding-slot reflow could silently drop real content** (beta.32). The beta.28 single-item-piece padding fix (below) could have real translated content reflow into the throwaway padding slot, silently discarded by a `.slice(0, 1)` trim. Now reconstructs the full result by joining every slot back together.
- **Selection-translate silently failing on short text** (beta.33). Page translation was fixed in beta.29 (below) to use the page's detected language instead of literal `'auto'`; the selection popup never got the same fix. Now shares the same detected-language fallback.
- **Silent-failure detector missed the short strings it was built for** (beta.33). The identical-output check only flagged results 40+ chars, but Google's silent-echo failure mode overwhelmingly hits short strings (nav labels, buttons). Now also flags any identical result whose script (CJK/Cyrillic/Arabic/etc.) doesn't match what the target language implies, at any length.
- **MathJax formulas, SVG icon text, icon-font ligatures mistranslated** (beta.33). Matched against TWP's real skip list: `<svg>`, `<template>`, `<math>`, `<mjx-container>`, `<tex-math>`, plus `material-icons`/`material-symbols-outlined` classes are now skipped — none were before.
- **`'auto'` source language silently failing** (beta.29). Google's auto-detection silently echoes text back unchanged (real `200`, no error) for a lot of real content. Page translation now sends the page's own detected language (via `tabs.detectLanguage`, with a text-sample fallback) instead of the literal string `'auto'`.
- **Single-string pieces unreliable on Google's endpoint** (beta.28). Google's endpoint only reliably translates a piece wrapped in `<a i=N>` markers, which only kicked in for multi-string pieces. Now every single-string piece is padded with a throwaway second string before sending.
- **Manually-pinned source language forced onto every future request** (beta.22). Selecting a language used to persist and override the provider's own per-request auto-detection forever. Now force-retranslates once, then a fresh page load goes back to auto-detection.
- **`<html lang>` falsely excluding whole pages** (beta.23). A per-node lang check almost always resolved to `<html lang>`, which reflects UI language, not content language (pixiv.net: `lang="en"` UI, Chinese novel content) — excluded 100% of matching pages. Check removed entirely, matching TWP (no equivalent check).
- **Tag/link clusters scrambled by cross-piece batching** (beta.5, beta.9, beta.27). Hashtags, `#go#be`-style chains, and nav/breadcrumb link clusters (`« Prev | Chapter 12 | Next »`) were batched into shared multi-item pieces and came back reordered/merged/scrambled. Each is now isolated into its own piece.
- **Shadow-DOM content structurally invisible to translation** (beta.13, and again more thoroughly at v0.2.1/Session 10). `element.childNodes` never includes shadow-root content — the DOM walk now crosses open shadow-root boundaries recursively.
- **Google reflow across grouped-node boundaries** (beta.13). Grouping multiple DOM text nodes into one request for extra context let Google reflow translated text across those internal boundaries (duplicated/merged fragments, stray leading punctuation). Reverted to one-node-per-piece for Google, matching every other provider.
- **`<pre>`/`<code>` defaults wrong** (beta.24, beta.25). `<pre>` was hardcoded skipped (broke prose-in-`<pre>` forum pages), then the "translate `<pre>`" toggle shipped defaulted off (broke it the other way) — TWP's real default is translate-on. Matched exactly, with the bare-whole-page `<pre>` exception TWP also has. `<code>` stays protected always.
- **No-letters text mistranslated** (v0.3.0-beta.16-adjacent). Chapter-count filter chips like `"> 100"` came back reworded as `"compare 100"`. Text with no letters at all is now skipped from collection.

### Checked and ruled out (don't re-verify from scratch)

- **HTML entity round-tripping** — `escapeHTML`/`unescapeHTML` handle `&amp; &lt; &gt; &quot; &#39;` correctly, decode-last ordering for `&amp;` verified live.
- **Language code coverage** — `zh/zh-CN/zh-TW/he/iw/no/nb/id/in/pt/pt-BR` all verified against the live endpoint; `zh-TW` correctly returns Traditional.
- **URLs, version strings, code snippets** pass through unmangled. One minor known gap, not scoped: `a.b@c.io` → `ab@c.io` (a dot dropped from an email local-part), low frequency.
- **Positional array alignment at scale** — verified directly at 40/120/300 pieces sharing one request: 0 misaligned. The batching-budget-based misalignment theory doesn't hold; the real reflow risk is within a single piece's `<a i=N>` markers, already handled separately.

### Open / deferred

- **Google sentence-context grouping (batchingHint) is designed but not implemented** (deferred out of beta.36 after investigation). The accuracy case is real and verified live: Google is currently one-node-per-piece (`descriptors.ts`, no `batchingHint`), so an inline `<b>`/`<a>`/`<span>` splits a sentence into fragments translated with zero context — measured "She left the party" → "Ella izquierda Llegó temprano" (left → the DIRECTION, not the verb) one-node-per-piece vs "Se marchó temprano" grouped; affects 48%/67% of Wikipedia's nodes/chars, 99% of HN's. Marker-order in the `<a i=N>` response is a verified perfect predictor of when grouped reassembly is safe (order-safe: es/fr/de/pt/sv/fi/id/vi/el; routinely reflows: ja/ko/zh/ar/hi/tr/ru/th). What blocked a same-session implementation: (1) the reflow signal needs the RAW per-piece response text, which isn't available where `google.ts`'s outer wrapper would need it without either extending the shared `batchedHttpProvider.ts`/`TranslateBatchRequest` interfaces, or a self-contained sentinel-value trick scoped to `google.ts` alone; (2) traced through beta.34's `onPieceComplete` (incremental write-back) and confirmed it fires BEFORE `google.ts`'s own padding/reflow reconciliation runs — a naive reflow fallback would flash garbled or sentinel text on screen for a moment before being corrected, a real user-visible regression; (3) a reflowed group just marked "missing" and left to the ordinary retry/regroup path risks re-forming the same group and reflowing again indefinitely — the fallback must be an immediate, contained re-request inside the same `translateBatch()` call, not routed through the generic repair mechanism. Getting all three right without regressing beta.34's speed win is a real design task — scoped out for its own pass rather than rushed. The live-endpoint verification data above and the reflow-safety detection approach (marker ascending-order check) are already validated and reusable when this is picked up.
- **`placeholder`/`alt`/`title`/`value` attribute translation is entirely unbuilt** (deferred out of beta.35 on request). Confirmed against TWP's live source (`getAttributesToTranslate`): they translate `input/textarea[placeholder]`, `area/img/input[type=image][alt]`, `input[type=button|submit|reset][value]`, and `body [title]`, honouring `.notranslate`/`translate="no"`. Prism translates no attributes at all — search boxes, image alt text, button labels, tooltips stay in the original language. Architecturally different from every other fix in this ledger: attributes aren't `Text` nodes, so none of `translateLoop.ts`'s existing collect/queue/write-back/restore machinery applies directly — needs its own small subsystem (closer in shape to `titleTranslator.ts` than to a bug fix), which is exactly why it was scoped out for its own dedicated design pass rather than rushed into beta.35 alongside 7 much narrower fixes.
- **Words still jam together at some block-level boundaries, independent of beta.33's node-level whitespace fix.** Found while spot-checking beta.34's live-page verification: live Wikipedia en→es shows 42 lowercase-then-uppercase jams — `"aplicaciones webOtro"`, `"modo privadoTambién"`, `"MozillaEl código"`, `"entoncesLos dispositivos"`. Confirmed NOT a beta.34 regression: rebuilt against a clean beta.33 checkout (`git stash`) and reran the identical probe — same 42 matches on both. So this is a real, currently-open gap beta.33's per-node whitespace restoration doesn't cover — likely two adjacent block-level elements (e.g. sentence-ending punctuation in one node, the next sentence's first word in a sibling node) where the SOURCE DOM itself has no literal space between the two text nodes and instead relies on CSS block rendering for the visual line break, so naive text-node concatenation loses it. Not yet root-caused or reproduced in isolation — worth a dedicated investigation (probably in `collectTextNodes.ts`'s node-collection order or `translateLoop.ts`'s write-back) before attempting a fix, since it's a different mechanism than the piece-level trailing-whitespace stripping beta.33 fixed.

## Speed

### Fixed

- **A whole tick's translated text was withheld until the slowest sub-request finished** (beta.34). `translateBatch()` resolved only once every underlying HTTP sub-request in a tick had completed, so a stalled sub-request held back dozens of already-translated pieces sitting in memory. `Translator` now supports an optional `onPieceComplete` callback, fired the instant each piece's own result is known; the page-translation engine writes it to the DOM right then. Verified live: first translated text visible in ~470ms on a real Wikipedia article.
- **Cache hits paid for an IndexedDB write just to read** (beta.34). `translationCache.getMany()` ran inside a `readwrite` transaction purely to bump each hit's recency timestamp in the same transaction — a fully-cached page revisit issued one IndexedDB write per text node. Reads now run in their own `readonly` transaction; the recency touch is a separate, unawaited transaction.
- **Every translated batch's reply waited on a non-essential cache write** (beta.34). `entrypoints/background.ts`'s `translatePieces` handler awaited the cache write (plus, on a cold worker, a full-store cursor scan) before replying — delaying DOM write-back for a write the code's own comment already calls "purely an optimization." Now fire-and-forget.
- **Per-request batching budget leaving throughput on the table** (beta.33). Measured directly: 300 pieces at ~800 chars/request took 674ms vs 107ms at ~6000 chars/request — per-request overhead dominates. Raised `DEFAULT_MAX_BATCH_CHARS` 800 → 2000 (moderate, not the full measured ceiling), verified end-to-end against real live Wikipedia through the built extension.
- **Google auth key re-scraped on nearly every translate** (beta.33). MV3 service workers suspend after ~30s idle and re-execute module scope on wake, so the 20-minute in-memory auth-key cache rarely survived. Now persisted to `browser.storage.session` and speculatively prefetched at background startup (fire-and-forget, overlaps other startup work).
- **Self-inflicted 150ms pause between every batch** (beta.31). Pure added latency unrelated to real network time. Removed; per-tick batch size raised.
- **Dead, unexplained 150ms startup delay** (beta.33). `originalLanguageTracker.start()`'s unconditional sleep had no comment justifying it and nothing downstream needed it. Removed.
- **Viewport-priority reordering re-measuring every tick** (graceful-degradation pass, beta.14-adjacent). Now only re-measures (`getBoundingClientRect()`, a real reflow cost) when something actually changed (scroll, new content), not on every tick of a long, static page.
- **Translation cache per-piece DB transactions** (beta.16-adjacent). Batched into single transactions per tick instead of one per piece; a persistent IndexedDB connection replacing open/close-per-write plus O(1) incremental size tracking instead of a full eviction scan per write (beta.5).
- **Fixed batching budget lowered as a blast-radius mitigation** (beta.22) — since superseded by the beta.33 measurement above, which found the misalignment theory behind keeping it low didn't hold at the tested scale.
- **Keepalive alarm ran unconditionally for the whole browser session** (beta.36). `entrypoints/background.ts`'s `chrome.alarms` keepalive ping used to be created once at startup and left running forever — waking the MV3 service worker every 24s (~2,880 times/day) even for a user who never translates anything. An audit-agent claim that the 0.4-minute period gets clamped to a 1-minute Chrome floor was checked directly (not trusted) via `chrome.alarms.getAll()`'s `scheduledTime` sampled over real wall-clock time — confirmed exact 24000ms deltas, no clamping. The alarm is now scoped to actual translate activity: created when a `translateText`/`translatePieces` handler starts (`beginTranslateActivity`/`endTranslateActivity`, ref-counted for concurrent in-flight translates), and self-clears once none are in flight. Verified via `tests/e2e/run.mjs` (alarm absent at idle startup, present during a real triggered translate) and extended live Playwright observation.
- **A periodic mutation-watcher timer forced a full-page resweep every ~500-750ms, forever, on any static page** (beta.37). `mutationWatcher.ts` ran its own interval that force-triggered `resweep.bump()` (resetting resweep's own 1.5s→10s adaptive backoff straight back to 1.5s) whenever the MutationObserver had seen nothing in the last window — but "the observer saw nothing" is the DEFAULT state of any page that simply isn't mutating, not evidence of a shadow-DOM-only mutation the observer structurally can't see, so this fired every single tick forever on the common case of a static page, forcing a full `document.body` walk continuously and defeating resweep's own backoff. Removed rather than patched (the naive "invert the condition" fix would have traded this for forcing a full walk on every tick of any continuously-updating page instead) — the mechanism was fully redundant with `resweep.ts`'s own already-independent, already-adaptive periodic walk, which exists for exactly this purpose.
- **The original-language detector forced a full synchronous page layout just to build a 4000-char text sample** (beta.37). The text-sample fallback read `document.body.innerText`, which (unlike `textContent`) reflects actual CSS rendering and so requires the browser to lay out the whole document first — real cost on the auto-translate-on-load critical path. Switched to a `TreeWalker`-based `textContent` read (no forced layout), which needed to keep excluding `<script>`/`<style>` element text itself (a naive `textContent` swap would pull raw JS/CSS text into the language-detection sample) — verified via a dedicated test asserting script/style markers never reach the sample sent to `i18n.detectLanguage`.
- **The two source-language detectors ran strictly serially, paying up to two full timeout windows back to back** (beta.37). `detectViaTab()` (an MV3 message round trip) used to be fully awaited before `detectFromPageText()` (the fallback) even started — each independently bounded at 3s, so an unanswered/slow relay paid its own full timeout, THEN the fallback's, on the auto-translate-on-load critical path, even though neither detector's input depends on the other's result. Now started together via `Promise.all`, capping the worst case at one timeout window while still preferring the tab relay's result whenever it isn't `'und'`. Trade: the local `i18n.detectLanguage()` call now always fires (previously skipped whenever the relay alone succeeded) — a cheap, non-network, no-longer-layout-forcing call, a fair price for halving the shared worst case.

### Checked and ruled out

- **Cross-piece misalignment as a reason to keep batches small** — directly disproven by measurement (see Accuracy's "Checked and ruled out" above). The real constraint is intra-piece reflow, not request bundling.

### Open / deferred

- None currently tracked as speed-specific open items beyond ordinary future audits. A future round could re-measure whether 2000 chars/request has more headroom now that real-page verification exists as a template — but treat any further raise with the same live-page-verification bar, given this constant's incident history (beta.22).

## Reliability

### Fixed

- **An individual-piece repair retry could double a request's worst-case time** (beta.34). The 30s overall deadline bounding a request's whole retry sequence was recomputed fresh for the individual-piece repair retry that fires when a batch response comes back short — so one `handleBatch()` could run ~60s, double what the constant's own doc comment says it enforces. The repair retry now inherits the parent's deadline instead of starting a new one.
- **The repair retry bypassed the request concurrency limiter entirely** (beta.34). A batch-wide failure (Google's documented silent-echo mode, or a truncated response) fanned out into one HTTP request per missing piece via a bare `Promise.all`, invisible to the `maxConcurrent` cap the top-level batch dispatch respects — up to dozens of simultaneous uncounted requests exactly when the endpoint is already struggling. Both paths now share one concurrency-limited dispatcher (`runWithConcurrencyLimit`).
- **A node that transiently detaches/reattaches (virtualized/recycled lists) could permanently lose its restore entry** (beta.33). The resweep backstop pruned a node's "restore to original" entry the instant it saw it disconnected — but a node reappearing with unchanged, already-translated content is never re-queued, so it stayed stuck translated forever. Pruning now requires two consecutive disconnected resweep ticks (extracted as `pruneDisconnectedRestoreEntries` in `translateLoop.ts` for deterministic unit testing, since the real resweep-scheduler/MutationObserver timing stack is interval-driven and not something a test can pin to an exact tick count).
- **Offline handling and retry backoff** (graceful-degradation pass, beta.14). Connectivity awareness (skip doomed requests while offline, resume instantly on reconnect), distinct "offline" vs. "provider broken" error states, jittered/extended retry backoff.
- **False-positive "Translation failed" from rapid retries** (beta.31). 3 failures within a fraction of a second (retries of the same stuck batch) used to count as confirmed-broken. Pre-surfacing retries are now genuinely spaced out.
- **`nodesToRestore` unbounded growth** (post-launch audit pass). Every node discovered while translated was added and never removed even after leaving the DOM — a long-lived SPA (infinite scroll, chat) leaked a strong reference to every detached node ever translated. Bounded via disconnected-node pruning (later hardened by the two-tick fix above).
- **`missingResultAttempts` was a lifetime cap, not per-episode** (post-launch audit pass). Never reset after a successful translation, so 3 non-consecutive transient failures over a session silently stopped retries forever. Now reset on success.
- **A totally-broken provider batch fell through silently** (post-launch audit pass, hardened further in beta.33's outputSanityCheck work). `createBatchedHttpProvider` always resolves (converts failed HTTP into `ok:false` per piece) — detecting "every outcome in this batch failed" now catches what used to fall through to a silent per-node give-up with no batch-level signal.
- **IndexedDB connection resilience** (beta.7). The persistent connection could be closed by the browser (common on mobile); now transparently reopens and retries once instead of failing every subsequent translate.
- **Firefox `i18n.detectLanguage` unbounded hang** (beta.20, beta.21). Mozilla bug 1712214 — can simply never resolve or reject. Two unguarded call sites (page-load detector, target-language-already check) now time out after 3s and fall back safely. Chrome was never affected, which is why it went unnoticed until Firefox releases became installable.
- **AMO signing silently broken across multiple releases** (beta.18–beta.21, beta.30). Manifest version collision (WXT strips the `-beta.N` suffix, every build produced identical `"0.3.0"`), then invalid/rotated JWT credentials (beta.28/29 both silently shipped unsigned zips). **Standing verification discipline this established**: always check the Release workflow's actual log text for `Signed xpi downloaded: ...`, never trust the green checkmark alone — the sign step uses `continue-on-error: true`, which can mask a real failure behind a misleadingly-green run.
- **Message sender spoofing** (beta.32, category: security/reliability overlap — see Security below).
- **A confirmed-suspicious-but-successful batch retried against Google's endpoint forever** (beta.36). Own regression, found via live observation while verifying the beta.36 keepalive fix (not a pre-existing bug): beta.35's `isSuspiciousOutcome` majority-threshold fix widened detection of "response looks like an untranslated echo" — correctly, but a real 200 OK for content Google legitimately declines to translate (a language's own endonym written in its own script — reproduced live on Wikipedia's language-switcher sidebar) keeps looking "suspicious" every single time, since a working provider returns the exact same result on every retry. `translateLoop.ts`'s `allFailed` handling didn't distinguish this from a genuinely-down provider, so it retried the whole batch unconditionally, forever, every tick — an unbounded request loop against a provider that was never actually broken. Fixed with a new `TranslateError` kind, `'suspicious'` (`src/engine/translator.ts`), threaded from `batchedHttpProvider.ts`'s repair-retry-exhausted point up through `PieceOutcome` (a provider-level `WeakSet<Promise<...>>`, not a per-call one, so pieces deduped into an already-in-flight identical request from a separate `translateBatch()` call correctly inherit the classification too — an earlier draft of this fix scoped the WeakSet per-call and silently broke that case). `translateLoop.ts` now takes the unconditional-retry-forever path only when a batch's failures are NOT all `kind: 'suspicious'`; an all-suspicious batch falls through to the per-node loop, which routes it through `noteMissingResult`'s existing bounded (give-up-after-3, cooldown-gated) retry instead. Verified live: request count to `translate-pa.googleapis.com` on a real Wikipedia page grew to completion then completely flatlined for 70+ seconds, versus unbounded growth beforehand.
- **A rapid same-node mutation storm could create duplicate queue entries** (beta.37). `requeueChangedTextNode` pushed onto `queue` with no membership check — a node changing more than once (a live score, a streaming counter) before its previous entry had been drained (`mutationWatcher.onChangedTextNode` calls this once per characterData mutation, unthrottled) accumulated a duplicate entry per change, wasting a translate request and racing two write-backs for one node. A direct regression test confirmed the actual severity: without a fix, ONE node changing twice produced THREE queue entries for it (two mutations plus the existing stale-write-back requeue path also lacking a check), not just two. Fixed with a simple `queue.includes(node)` guard before pushing.
- **`translationRoutine` could run two concurrent ticks for the SAME translate cycle** (beta.37). `wakeRoutine()` only ever cancels a PENDING (not-yet-fired) scheduled call via `clearTimeout` — it can't stop an invocation already mid-`await` (e.g. awaiting a `translateBatch()` HTTP round trip). A wake fired while a tick was still in flight for the same cycle (the mutation-storm scenario above, each mutation calling `wakeRoutine()`) used to schedule and immediately run a fully concurrent second tick, racing shared `queue`/`batchInFlight` state — `isWorking()` could report "done" while a batch was still genuinely in flight, and both ticks independently scheduled their own next run, doubling the effective polling rate. Fixed with a re-entrancy guard keyed by `cycleGeneration` (not a plain boolean): a plain lock would have also blocked the INTENTIONAL, already-tested case of a fresh `translatePage()` call needing to start draining its own new queue immediately while an old, abandoned cycle's batch is still resolving in the background — keying on generation blocks only a truly redundant re-entrant tick for the SAME cycle while still letting a new cycle run concurrently with an old one winding down.
- **`resweep.ts`'s scroll listener never saw an inner scroll pane's scroll events** (beta.37). Registered as a plain bubbling-phase `window` listener — but a `'scroll'` event fired on an ELEMENT (not `window` itself) never bubbles per the DOM spec, so an app-shell layout with a fixed header/sidebar and a scrolling content area (a common real-world layout) never bumped resweep's cadence on scroll, unlike a plain-document scroll. Fixed by adding `capture: true`: every `'scroll'` event, regardless of target, passes through `window` during the capture phase on its way down — the one phase a non-bubbling event still traverses.

### Checked and ruled out

- Nothing specific logged yet in this category — reliability findings so far have all led to real fixes.

### Open / deferred

- None currently tracked.

## Security

### Fixed

- **No message-sender validation** (beta.32). `@webext-core/messaging`'s `onMessage` does no sender validation of its own (checked its actual implementation directly). Any other installed extension could send this extension's own message shapes straight to its background/content script and have them processed as if from this extension's own UI — triggering translate/restore, or relaying arbitrary text through `translatePieces` to spend the user's configured provider quota (including a paid key). Every handler in `entrypoints/background.ts` and `entrypoints/content.ts` now rejects unless `sender.id` matches `browser.runtime.id`.

### Checked and ruled out

- Nothing specific logged yet — the beta.32 round found exactly one real issue and it's fixed above. A later round explicitly deprioritized further security work ("security is fine for now") in favor of speed/accuracy — that's a scoping choice for that round, not a finding that nothing else exists. Re-open security as a category on request.

### Methodology notes carried forward

- **Cast a wide net before narrowing.** Run parallel probes/greps covering multiple hypotheses at once, then go deep on what's real — not one hypothesis investigated to conclusion before starting the next. (Direct user correction, round 2: "it looks like you look one at a time and then get stuck at one.")
- **Verify empirically, not by inference.** Live-endpoint `fetch` probes for provider behavior claims, `gh api` against TWP's real source for "what does the reference implementation do" claims — not assumption or memory.
- **Revert-and-confirm-fails on every fix.** Temporarily break the new logic, confirm the new test fails with the expected message, restore, confirm it passes again.
- **Full real-page verification for anything with prior incident history**, not just unit tests — the batch-size constant specifically (beta.22 history) got a real Playwright run against live Wikipedia through the actual built extension, not just synthetic benchmarks. This is what surfaced the whitespace bug that the unit-test-only rounds had missed.
- **Be precise about progress counts.** Don't bundle a bonus fix found along the way into the count of a numbered finding list — report them separately (direct user correction, round 2).
- **Verify AMO signing via actual log text**, not the green checkmark, every release — see Reliability's AMO entry above.
- **A live-page regression check that looks bad isn't necessarily a regression — confirm against a clean baseline before assuming.** Round 3 part 1's live verification found 42 word-jamming matches on Wikipedia after shipping; before treating it as a new bug, `git stash`'d the changes, rebuilt against the unmodified prior release, and reran the identical probe — same 42 matches, proving it pre-existing (now tracked in Accuracy's Open/deferred). Cheap and fast (a stash + rebuild), and the only way to distinguish "I introduced this" from "this was already here."
- **`batchedHttpProvider.ts`'s own test file has a misleading comment**: `maxBatchChars: 1, // force every piece into its own request` (in the "caps concurrent in-flight" test) does NOT do what it claims — a 1-char piece only reaches `currentChars = 1`, which fails the `> 1` flush check, so it merges with the next piece instead of splitting. That test still passes with the expected request count, but only because of an unrelated repair-retry side effect (the mocked response returns fewer results than pieces sent, triggering individual repair requests), not because of the batching split the comment describes. Found and worked around (used `maxBatchChars: 0`, which genuinely does force a per-piece split) while writing round 3's own concurrency test — not fixed, since it's a pre-existing test only, not product code, and touching it was out of this round's scope. Worth a real look next time that test file is touched.
- **A new "reject stale state" check can trip on the fix's OWN intentional side effects — check for that interaction explicitly, don't just test the new check in isolation.** Round 3 part 2's stale-overwrite fix (`sentText` map, compares `node.data` against what was actually sent before writing) initially produced `"TR:TR:score: 2"` — double-translated — in its own first test run. Cause: the incremental-write-back feature from part 1 deliberately calls the write-back function TWICE per node in the same tick (once via `onPieceComplete`, once again from the always-running final loop, by design — see `writeTranslatedNode`'s doc comment) and relies on that being a harmless no-op. The new staleness check broke that invariant: after the FIRST write, `node.data` no longer matched the ORIGINAL `sentText` entry (it now held the TRANSLATED text), so the redundant SECOND call saw a "mismatch" and mistook its own prior write for an external page update, re-queueing the node to re-translate its own output. Fixed by updating `sentText` to the new value immediately after a successful write, so the redundant pass sees no mismatch. The lesson: when adding a check that compares "what we expect" against live state, audit every OTHER place in the same function/file that also touches that live state — not just the new check's own direct test cases — since two independently-correct pieces of logic can still interact wrongly.
